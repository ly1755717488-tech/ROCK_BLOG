## 一、先理解 DSH 的整体知识管理体系

这篇文章真正值得学习的地方，是它提出了一套解决 AI 编程长期维护问题的方法：

让 AI 不仅知道项目现在是什么样，还要知道项目为什么会变成现在这样。

其中，docs/ 和 agent notes 是两个非常重要的组成部分。

- docs/：让 AI 理解项目当前的真实状态，解决「现在是什么」的问题。
- agent notes：让 AI 理解项目过去的决策和经验，解决「为什么这样做」的问题。

两者配合，才能让新开启的 Agent 会话继承项目知识，而不是每次都从代码中重新猜测。

![DSH 三层知识体系](/img/dsh-notes/01-three-layer-knowledge.png)

### 三层知识管理体系

```text
第一层：AGENTS.md
规则层 · How
告诉 Agent 应该遵守什么规则、如何工作
        ↓
第二层：docs/
事实层 · What
告诉 Agent 项目当前的架构、模块职责、运行机制和开发规范
        ↓
第三层：.agents/notes/
决策层 · Why
告诉 Agent 过去做过什么决策、为什么选择当前方案、哪些方案曾被否定
```

这三层不是简单的目录分类，而是三种不同性质的知识。

### AGENTS.md：规则层

告诉 Agent 应该遵守什么规则、如何工作。例如：

- 项目使用什么语言、框架和工具链。
- 修改代码前应该先读哪些文档。
- 代码风格、测试要求和提交规范是什么。
- 哪些操作需要先征求开发者同意。
- 完成任务后必须执行哪些验证。

根目录放通用规则；关键子目录也可以放自己的 AGENTS.md，让 Agent 在对应模块工作时读取局部规范。规则文件应保持精简，避免无限膨胀。

### docs/：事实层

告诉 Agent 项目当前的架构、模块职责、运行机制和开发规范。重点是当前真实状态，而不是完整的历史过程。

### .agents/notes/：决策层

告诉 Agent 过去做过什么决策、为什么选择当前方案、哪些方案曾经被否定，以及这些决策带来的约束和代价。

## 二、docs/：项目当前事实的知识库

核心定位：描述当前系统。

### 1. docs 解决什么问题？

假设你新开一个 Codex 会话，让它修改用户认证模块。AI 需要先搞清楚：

- 整个项目采用什么架构？
- 认证模块负责什么？
- 认证模块和其他模块怎么交互？
- 登录状态如何流转？
- 哪些接口和数据结构不能随便修改？
- 项目有哪些开发规范？

这些信息不能每次都靠 AI 阅读几百个源代码文件自行推断。

因此，使用 docs/ 保存整理好的项目知识，让它成为 AI 理解项目当前状态的基础知识库。

### 2. docs 的目录组织

可以把 docs 分成四类：

```text
docs/
├── architecture.md
├── subsystems/
│   ├── auth.md
│   ├── database.md
│   └── messaging.md
├── cookbook/
│   ├── development.md
│   ├── debugging.md
│   └── deployment.md
└── postmortem/
    └── incident-2026-01.md
```

| 分类 | 主要内容 | 回答的问题 |
| --- | --- | --- |
| `architecture.md` | 系统架构全景、核心组件、模块关系、关键设计约束 | 整个系统是如何组织的？ |
| `subsystems/` | 子系统职责、内部机制、运行语义、模块契约 | 这个模块具体是怎么工作的？ |
| `cookbook/` | 开发、调试、部署、排查问题等实际操作方法 | 遇到某个开发任务应该怎么操作？ |
| `postmortem/` | 故障现象、影响、原因和改进措施 | 之前发生过什么问题，如何避免再次发生？ |

### architecture.md：系统架构全景

描述整个项目的架构、核心组件、模块关系、关键设计约束。

解决的问题：整个系统是如何组织的？

### subsystems/：子系统规范

分别描述各个子系统的职责、内部机制、运行语义和模块契约。

解决的问题：这个模块具体是怎么工作的？

### cookbook/：操作手册和开发指南

记录开发、调试、部署、排查问题等实际操作方法。

解决的问题：遇到某个开发任务应该怎么操作？

### postmortem/：事故复盘

记录故障现象、影响、原因和改进措施。

解决的问题：之前发生过什么问题，如何避免再次发生？

### 3. docs 最重要的维护原则

### 原则一：只记录当前事实，不记录历史流水账

例如，不推荐：

```text
以前系统使用 Session V1，
后来升级到 V2，
现在已经不再使用 V1。
```

推荐：

```markdown
# Session Architecture

系统使用 Session V2 进行会话管理。

Session 由 SessionManager 创建和维护。
所有会话状态变更必须经过 SessionManager。
```

为什么？

因为 docs 是当前系统的说明书，不应该变成项目开发历史记录。历史决策交给 Agent Notes。

### 原则二：文档分层，不要把所有东西塞进一个文件

不要把架构、模块说明、部署指南、故障记录全部写进一个 README.md。

否则：

- 文档越来越长。
- Agent 查找信息越来越困难。
- 修改某个模块时容易遗漏相关信息。
- 不同 Agent 并行修改文档容易冲突。

### 原则三：文档必须有质量约束

- 限制每篇文档的长度，避免无限膨胀。
- 不允许无意义的内容堆积。
- 不鼓励手工复制 API 清单。
- 避免文档快速过期。
- 可以通过 CI 检查文档格式、链接、长度或必需章节。

这实际上是在防止 AI 不断生成文档，却没有真正增加项目知识。

### 4. docs 在实际开发中的作用

假设你让 Codex 修改支付模块，它可以按照这样的方式工作：

- 先读取 docs/architecture.md，理解系统架构。
- 再读取 docs/subsystems/payment.md，理解支付模块。
- 查看相关 cookbook/，了解项目开发和测试方式。
- 根据这些事实修改代码。
- 修改完成后同步更新受到影响的 docs。

这样 docs 就成为 AI 理解项目的基础知识库。

一句话：docs 是项目当前状态的说明书。

## 三、Agent Notes：项目工程决策记忆库

核心定位：记录决策背后的原因。

这部分是整篇文章最有价值的内容。

### 1. 为什么有了 docs，还需要 Agent Notes？

看一个典型例子。

假设你的项目中有这样一段代码：

```javascript
async function processMessage(message) {
  // 复杂的消息处理逻辑
}
```

新来的 AI 看到代码后，可能认为：

- 逻辑太复杂。
- 性能不够好。
- 可以简化。
- 可以改成另一种实现。

于是它进行了重构。

但它不知道：这段复杂逻辑是之前为了解决并发问题，经过多次尝试和线上验证后才确定的。

新方案看起来更漂亮，却可能重新引入之前已经解决的 Bug。

这就是 AI 编程中的一个典型问题：

代码能告诉 AI 怎么实现，却不一定能告诉 AI 为什么必须这样实现。

Agent Notes 就是解决这个问题的。

它记录：

- 当时遇到了什么问题？
- 为什么选择当前方案？
- 考虑过哪些替代方案？
- 为什么否定其他方案？
- 当前方案有什么代价？
- 哪些约束不能随意突破？

### 2. 一篇 Agent Note 应该包含什么？

最重要的不是写多长，而是把决策过程记录完整。

可以采用下面五部分结构：

### 01. Problem / Background

问题背景：为什么需要做这个决策？

例如：项目中出现多个模块直接调用内核，导致模块耦合。

### 02. Decision

最终决策：最终确定了什么方案？

例如：所有跨模块通信必须经过统一消息通道。

### 03. Alternatives Considered

被放弃的方案：考虑过什么，为什么不采用？

例如：

- 直接调用内核：耦合太强。
- 共享全局状态：难以控制并发。
- 消息通道：增加序列化成本，但边界清晰。

### 04. Consequences

决策后果：收益和代价分别是什么？

例如：模块解耦程度提高，但通信链路增加了一层。

### 05. References / Validation

代码关联与验证：哪些代码实现了这个决策？测试如何证明它有效？

例如：相关模块路径、代码锚点、测试文件和关联 Note。

一篇 Note 可以写成：

```markdown
# 决策标题

## Problem / Background
问题背景：为什么需要做这个决策？

## Decision
最终决策：选择了什么方案？适用范围是什么？

## Alternatives Considered
考虑过哪些替代方案？各自的优缺点是什么？为什么没有采用？

## Consequences
这个决策带来了什么收益、代价和后续约束？

## References / Validation
相关代码路径、测试文件、设计资料和验证结果。
```

这五部分是对决策信息的结构化归纳，并不是说每一篇 DSH 笔记都必须采用完全相同的标题。

### 3. Agent Notes 最核心的功能

我认为主要有四个。

### 功能 A：防止 AI 重复踩坑

假设之前已经测试过：

- SQLite 不适合当前并发模型。
- 多进程方案增加了部署复杂度。
- Redis 方案不符合当前运行环境要求。

如果这些结论只存在于之前的聊天记录里，新会话就可能重新提出这些方案。

如果记录在 Notes 里，Agent 可以先检索历史决策，避免重复讨论。

### 功能 B：防止 AI 擅自重构

这是非常重要的功能。

例如，某段代码看起来不够优雅，但它实际上承担了特殊兼容逻辑。

Note 可以告诉 AI：

```text
这段逻辑必须保留。

原因：
之前尝试过统一处理，
但会破坏旧版本客户端的兼容性。

禁止在没有完成兼容性验证的情况下
删除该处理逻辑。
```

AI 在修改代码前，就能理解这个设计背后的约束。

### 功能 C：保留被否定的方案

普通项目的文档经常只记录最终结果。

但对于 Agent 来说，知道哪些方案被否定过同样重要。

因为 AI 很容易重新提出一个看似合理、实际上已经被验证失败的方案。

### 功能 D：让项目的工程知识随代码一起演进

Note 不应该只是开发者电脑里的私人笔记。

它应该和项目代码一起放在 Git 仓库里。

这样：

- 新成员可以了解历史决策。
- 新会话可以查阅之前的经验。
- 代码回滚时可以追溯设计背景。
- 团队成员能够共享工程知识。

### 4. 什么时候需要写 Agent Notes？

注意：不是每次改代码都要写。

重点是非平凡改动（Non-trivial Changes）。

| 修改类型 | 是否需要 Note |
| --- | --- |
| 修改按钮颜色 | 不需要 |
| 调整 CSS 样式 | 不需要 |
| 修复简单拼写错误 | 不需要 |
| 普通 CRUD 修改 | 通常不需要 |
| 修改核心架构 | 需要 |
| 修改模块之间的通信协议 | 需要 |
| 更换数据库或存储方案 | 需要 |
| 修改核心状态流转机制 | 需要 |
| 改变依赖管理策略 | 需要 |
| 修复复杂并发问题 | 需要 |
| 修改测试策略或发布流程 | 视影响程度，通常需要 |

一个简单的判断标准：

如果未来的 Agent 可能会重新考虑这项决定，或者不知道当时为什么这么做，那么就值得写 Note。

文章也特别强调，不要把 Notes 写成每日工作流水账。

### 5. Agent Notes 如何与代码关联？

这是 DSH 很值得借鉴的设计。

它不是把 Notes 独立放在那里，等 AI 有空才去看，而是尽可能建立代码到决策记录的关联。

例如，在代码中：

```javascript
// Note: .agents/notes/architecture/message-bus.md
async function processMessage(message) {
  // ...
}
```

当 Agent 修改这段代码时，就能顺着注释找到对应的工程决策。

这有三个好处：

- 不需要每次加载整个 Notes 目录。
- 修改代码时可以精准找到相关历史背景。
- 让代码实现和决策文档形成双向关联。

另外，DSH 按目录对 Notes 分类管理，而不是维护一个全局 INDEX.md。

原因是多个 Agent 在不同分支并行开发时，如果每新增一篇 Note 都要修改同一个索引文件，很容易发生 Git 冲突。

### 6. Agent Notes 应该如何演进？

这里还有一个很重要的思想：

新的决策取代旧决策时，不要直接篡改历史结论。

例如：

- 2026 年 1 月：决定使用 SQLite。
- 2026 年 3 月：发现业务并发需求发生变化。
- 2026 年 3 月：决定迁移到 PostgreSQL。

正确的方式是：

- 新建 PostgreSQL 的决策 Note。
- 说明为什么旧方案不再适用。
- 关联之前 SQLite 的 Note。
- 将旧决策标记或迁移为已被取代的历史记录。
- 更新 docs，让它反映当前使用 PostgreSQL 的事实。

这样可以同时保留：

- 当前系统究竟使用什么。
- 为什么从 SQLite 迁移到 PostgreSQL。
- 当初为什么选择 SQLite。
- 旧方案在什么条件下不再适用。

这就是文章所强调的：升级不去修改旧的结论，只做新增和迁移。

一句话：Agent Notes 是项目工程决策的记忆库。

## 四、docs 和 Agent Notes 的本质区别

这是最值得记住的一张表。

| 对比维度 | docs | Agent Notes |
| --- | --- | --- |
| 核心定位 | 项目事实知识库 | 工程决策知识库 |
| 回答的问题 | 现在是什么样 | 为什么变成这样 |
| 主要内容 | 架构、模块、接口契约、操作规范 | 决策背景、方案取舍、踩坑经验 |
| 关注重点 | What / How | Why |
| 主要读者 | 开发者、Agent | 未来维护者、新 Agent |
| 更新方式 | 随当前系统变化而更新 | 新决策增加，旧决策保留并迁移 |
| 主要价值 | 帮助 AI 正确理解系统 | 帮助 AI 避免重复犯错 |
| 典型风险 | 文档过期、事实不准确 | 决策丢失、重复讨论、错误重构 |

### 用一个真实开发场景理解两者

假设你正在开发一个 AI Agent 平台，其中采用了消息队列进行模块通信。

docs/subsystems/messaging.md

记录：

```markdown
# Messaging Subsystem

## Overview

系统使用统一消息总线进行模块间通信。

## Rules

1. 模块间通信必须经过消息总线。
2. 不允许直接访问其他模块的内部状态。
3. 消息必须遵循统一的数据结构。
```

它告诉 AI：现在系统是怎么运行的。

.agents/notes/architecture/message-bus.md

记录：

```markdown
# Agent Note: 采用统一消息总线

## Problem

多个模块直接调用其他模块，
导致模块之间高度耦合。

## Decision

所有模块间通信统一使用消息总线。

## Alternatives Considered

- 直接函数调用：实现简单，但耦合较高。
- 共享全局状态：并发和状态一致性难以保证。
- 消息总线：增加通信开销，但模块边界清晰。

## Consequences

收益：
- 降低模块耦合。
- 支持模块独立演进。

代价：
- 增加序列化和消息分发成本。
- 调试链路更加复杂。
```

它告诉 AI：为什么当初选择消息总线。

两者结合，AI 就不容易为了减少一层调用而直接破坏整个架构。

## 五、docs 和 Agent Notes 如何形成完整工作流？

我认为可以把 DSH 的设计总结成下面这套闭环：

```text
flowchart TD
    A["理解项目：读取 AGENTS.md"] --> B["查阅 docs：理解当前架构和模块事实"]
    B --> C["检索 Notes：了解历史决策和约束"]
    C --> D["制定方案：明确改动范围与验收标准"]
    D --> E["实施开发：遵循架构边界修改代码"]
    E --> F["更新知识：同步 docs，必要时新增 Note"]
    F --> G["运行测试与 CI：验证代码和文档"]
    G --> H["提交变更"]
```

具体步骤：

- 理解项目：读取 AGENTS.md，明确工作规则；查阅 docs，理解架构和模块契约。
- 检索历史决策：搜索 .agents/notes/，检查当前任务涉及的历史约束和被否决方案。
- 制定方案：如果是重要改动，先整理背景、备选方案、最终决策和验收标准。
- 实施开发：按照架构约束修改代码，不随意突破已有模块边界。
- 更新知识：修改当前事实文档 docs，新增或更新相关 Agent Notes，补充代码锚点。
- 验证与提交：执行测试、文档检查和相关规范检查，确保代码和知识记录同步。

测试管当下，笔记管未来。

测试确保当前代码没有破坏已有行为；Notes 则尽可能防止未来的 Agent 忘记历史约束，再次破坏这些行为。

## 六、我建议如何借鉴到自己的项目？

不建议一开始就完全照搬 DSH 的复杂程度。

可以先采用下面这个精简目录：

```text
your-project/
│
├── AGENTS.md
│
├── docs/
│   ├── architecture.md
│   ├── subsystems/
│   │   ├── auth.md
│   │   ├── database.md
│   │   └── messaging.md
│   ├── cookbook/
│   │   ├── development.md
│   │   └── deployment.md
│   └── postmortem/
│
├── .agents/
│   └── notes/
│       ├── architecture/
│       ├── database/
│       ├── feature/
│       ├── bug-fix/
│       └── process/
│
└── src/
```

### 建议逐步增加三种管理机制

| 机制 | 解决的问题 | 优先级 |
| --- | --- | --- |
| AGENTS.md 规则 | AI 是否知道应该读什么、遵守什么 | 高 |
| Note 代码锚点 | AI 修改代码时是否能找到对应决策 | 高 |
| CI 文档及 Note 检查 | AI 是否真正遵循文档维护规范 | 中高 |

## 七、最后说说我的理解：这套设计最有价值的是什么？

我认为 DSH 的这套方法解决了 AI 编程中三个长期存在的问题：

### 1. 知识连续性

Agent 每次都可能开启新会话，但项目知识不应该随着会话结束而丢失。

### 2. 决策可追溯性

Agent 不应该只知道某个规则，还应该知道规则背后的原因和代价。

### 3. 工程可维护性

每次重要修改都能沉淀知识，让后续开发在已有经验上继续，而不是不断推倒重来。

不过，也有三个实际风险值得注意：

- Token 成本：不能每次都把全部 docs 和 Notes 塞给 Agent，应该按模块、代码锚点和任务检索。
- 知识腐化：docs 可能过期，Notes 可能与新架构冲突，因此需要定期检查和明确的替代关系。
- 流程过重：个人小项目不需要为每个小改动写决策文档，应该只记录真正影响长期维护的决定。

## 八、最终建议

如果你打算长期使用 Codex 或 Claude Code 开发一个项目，我会优先建设：

- AGENTS.md：让 AI 知道工作规则。
- docs/：让 AI 知道系统当前的真实状态。
- .agents/notes/：让 AI 知道历史决策和经验。
- Tests + CI：让 AI 的修改受到客观验证。

这四部分结合起来，才真正形成一个可以随着项目长期演进的 AI 工程知识体系。
