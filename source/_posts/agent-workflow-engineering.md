AI Coding 用久了会发现一个现象：流程写得越细，Agent 反而越容易出错。不是因为它不听话，而是因为它把注意力花在了理解流程上，而不是解决问题上。

所以这套工作流的目标不是把 Agent 固化成按步骤执行的脚本，而是在给它合理自主权的前提下，让复杂任务稳定落地。

## 一、工作流管理的对象是不确定性

Agent 干活时会遇到六类不确定性：

1. **任务不确定性**：需求理解偏差、歧义、隐含条件遗漏
2. **执行不确定性**：偏离方案、擅自扩大修改范围
3. **协作不确定性**：多 Agent 改同一个文件、任务依赖丢失
4. **结果不确定性**：产出不符合设计、藏着架构缺陷
5. **操作与资产风险**：误提交、强制推送、文件覆盖、资产泄露
6. **知识流失风险**：任务结束，经验和决策跟着会话一起消失

这些问题的共同点是，它们都不发生在「Agent 敲下这一行代码」的瞬间。

核心结论是：**工作流的管控重心是任务、上下文、依赖、执行权限、验证证据和知识沉淀，而不是 Agent 的每一步操作。**

还有一条底层原则容易被忽略：**工作流要跟着模型能力走，不能一成不变。**

早期模型推理和遵从性都弱，工作流得替它拆解任务、写长指令、设密集门禁。模型变强以后，过重的流程就成了负担，Agent 要花大量上下文去理解规则，甚至去找绕过规则的路子。

正确做法是反向收缩：模型越强，工作流越要从「详细步骤指令」转向「目标约束、状态管理、风险阻断、结果验证」。只盯模型自己保证不了的环节，不重复教它已经会的事。

## 二、架构：方法论、调度、执行工具要分开

一套跑得顺的组合，职责通常是这样切的：

| 组件 | 职责 |
| --- | --- |
| Trellis | 任务设计、调度分发、多 Agent 派发、执行记录、项目任务管理 |
| Superpowers | 工程方法论、需求梳理、PRD、设计评审、实施检查、质量验证 |
| CLI | 统一操作入口，封装可执行、可校验的原子操作 |
| OpenSpec | 任务结构、文档组织、状态流转、归档管理 |
| write-note-like-deepseek-harness | 上下文沉淀、知识记录 |

这五层最忌讳的是耦合。方法论负责定义 Agent 要想什么、查什么；任务调度负责维护进度、依赖和任务谱系；CLI 负责把操作标准化，自带校验。

一旦把三者揉在一起，改一条规则就要动整套流程，维护成本立刻上去。拆开之后，可以按模型能力和项目规模单独调整某一层。

### CLI 为什么值得单独抽出来

把归档、审批、任务记录、证据收集、临时文件清理、Git 操作都收进 CLI，收益很具体：

- Agent 不用自己拼高危、复杂的命令
- 多 Agent 的操作规范统一
- 工作流状态集中记录，可追溯
- Skill 提示词能大幅缩短，不用反复说明
- 操作结果可以自动校验

但边界也要说清楚：CLI 不是通关式的复杂系统，它只回答三件事，当前状态是什么、缺哪些条件、下一步建议做什么。

## 三、门禁：硬门禁挡风险，软门禁给提醒

| 类型 | 核心职责 | 适用场景 |
| --- | --- | --- |
| 硬门禁 | 确定性校验、高危操作阻断 | 文档结构校验、必填字段检查、授权校验、危险操作拦截 |
| 软门禁 | 上下文感知提醒、流程纠偏 | 复核提醒、冲突提示、等待用户确认、派发建议 |
| 普通建议 | 决策参考 | 任务拆分、并行方案、实现思路 |

### 硬门禁只做机器能判定的检查

只拦截确定性的高风险动作，不要把主观评审塞进硬规则。

比如 `workflow plan --validate`，它校验方案文档的结构、必填项、前置验证有没有完成，但不负责判断这个方案好不好。方案质量交给人和独立复核。

### 软门禁负责即时反馈

软门禁不阻断操作，只在动作触发时给上下文提示：还没审批、缺少独立复核、存在文件冲突、提交范围待确认、需要问用户。

它比一次性灌一大段流程 Prompt 有效得多。Agent 在具体操作的那一刻收到提醒，能结合当前上下文判断，而不是提前背一堆规则。

### 门禁越多不等于越安全

如果 Agent 为了完成任务一直在绕门禁，门禁本身就成了额外成本。

加门禁之前先问两句：这个必须阻断吗？能不能改成日志记录加事后验证？

## 四、高危操作：授权要留痕，范围要可控

### 授权必须落盘

commit、push、任务派发、方案批准这些动作，不能信 Agent 单方面的声明。

流程是：Agent 先输出操作说明，写清变更范围、影响、目标，然后落盘记录；CLI 校验授权记录，没有授权直接拦截；用户授权后再做一次校验才放行。这样就把「意图」和「执行权限」分开了。

### 授权要限定作用域

授权有两种形式：用户手动执行 CLI 批准命令，或者在当前 Task 内开放部分权限。

不管哪种，都要绑定四件事：所属任务、允许的操作、文件和分支范围、失效条件。**push 单独设最高等级权限。**

### 软提示不能替代硬校验

这条底线要反复强调。软门禁只做引导，高危操作的执行入口必须再硬校验一次授权。不能依赖 Prompt、Skill 或者 Agent 自证。

## 五、Git 与资产隔离

### 个人资产和项目资产要分开

- 个人资产：工作流配置、个人画像、任务记录、调度日志、个人知识库
- 项目资产：源码、团队共享文档、正式设计、交付产物

公司仓库只提交项目资产。个人工作流的运行状态不该入库，混进来就是噪音，还可能是泄露。

### Commit 和 Push 的边界

小修改合并提交，独立大功能单独提交，无关变更别硬凑在一起，格式遵循 Conventional Commits。

Push 则保留给用户。Agent 可以完成开发、自测、准备 commit，但推送这一步交给人执行。这个成本很低，却能规避版本覆盖和资产泄露。

## 六、多 Agent 并行：按依赖切，按 Worktree 隔离

### 并行与否看依赖，不看任务数量

- 修改范围完全独立：可以并行
- 文件范围有交集：默认串行
- 存在前置依赖：等前置完成
- 能拆出独立子任务：拆出来并行

盲目拆任务是最常见的浪费。拆完还要重建上下文、整合结果，协调成本可能比省下的时间还多。

### 派发阈值

小任务直接由主 Agent 处理。只有工作量、独立性、专业性都够了，才派子 Agent。

- 持久化队员：大范围改代码、复杂模块开发、架构调整、多轮返修
- 一次性子 Agent：独立复核、代码检查、技术调研、方案对比、收敛检查

同时要设并行上限，不然 Token、上下文和协调成本会一起爆。

### 派发前先跟用户确认调度方案

主 Agent 输出拆分结果、子任务边界、依赖图、串并行安排、冲突风险和 Agent 类型，用户确认后再启动。

### Worktree 做物理隔离

独立任务分配独立的 Git Worktree，各自在隔离工作区里改、自己测。主 Agent 统一收集变更、核验证据，用户验收后再合并回主分支。同目录覆盖和状态污染的问题，从根上就没了。

## 七、独立复核与多轮收敛

### 单上下文自闭环的盲区

在同一个 Session 里自我审查，方案会带着隐含假设往下走，自己查不出自己的漏洞。典型表现是需求遗漏、前后矛盾、范围模糊、依赖缺失、实现偏移。

### 至少两个干净上下文

复核由两个干净上下文的独立子 Agent 来做。目标不是让它点头同意，而是主动挖缺陷：需求漏了什么、假设哪里不合理、哪里有歧义、有没有 P0/P1 阻断问题、范围边界清不清楚。

### 收敛靠退出标准，不靠固定轮数

流程是：主 Agent 输出 PRD 或设计文档，两个独立 Agent 分别复核，问题分级汇总，主 Agent 修复，再换新的干净上下文复检，循环到收敛。

退出标准是这几条同时满足：

- 没有未解决的 P0 阻断问题
- P1 风险已处理，或者明确接受
- 需求、设计、实施范围一致
- 没有重大歧义
- 关键风险都有验证手段
- 复核不再产出新的实质问题

复杂重构和底层架构调整，通常要 3 到 5 轮才能收敛。

### 多模型交叉复核

不同模型的推理偏好和知识盲区不一样，交叉检查更容易发现单点遗漏。但模型提出的问题仍要拿代码和业务事实去判断，不能自动采信。

## 八、知识沉淀要写进任务生命周期

会话一结束，子 Agent 一销毁，没人主动记录，经验就直接没了。所以沉淀不能靠 Agent 自觉，得做成强制环节。

沉淀分两类：

- **项目画像**（长期静态）：业务背景、技术栈、架构模块、约束、规范、环境
- **知识记录**（动态实践）：验证方案、踩坑点、关键决策和原因、特殊业务逻辑、调试结论、失败方案复盘

机械约束是：每个 Task 完成必须产出有效知识记录，或者明确说明本次没有可沉淀的内容。只记可复用的，不堆原始日志。

## 九、任务状态与任务谱系

任务状态参考 OpenSpec 的模型：

- 活动任务：Plan（需求、方案）、Build（开发实施）、Verify（验证验收）
- 归档任务：Done（完成）、Abandoned（放弃）

任务路线变了、范围调了、换人接管或者中断时，不要直接转发原始对话，而是生成一份交接文档：原始目标、已完成内容、当前状态、已验证结论、遗留问题、风险、新目标、验收标准。

还有一个容易被忽略的东西，任务谱系。普通列表表达不了派生、接管、拆分、替代、废弃这些关系。建一张二维的任务关系图谱，才能回答「这个项目为什么变成现在这样」。

## 十、十二条可复用原则

1. 工作流服务于模型，不是模型服务于工作流
2. 硬门禁只用于确定性校验和高危风险阻断
3. 优先在操作时给即时反馈，少一次性注入海量 Prompt
4. 调度以依赖关系和修改交集为核心，并行不是越多越好
5. 高危操作必须留痕授权，不依赖 Agent 自证
6. 并行修改必须有隔离机制，比如 Worktree
7. 重要设计必须经过独立上下文复核
8. 验收以客观证据为准，不采信 Agent 单方面说完成
9. 知识沉淀是生命周期的强制环节，要配机械检查
10. 任务除了状态，还需要谱系来记录演化链路
11. 用户控制权集中在关键决策和高危操作，不介入细碎步骤
12. 工作流从失败案例迭代，新增机制必须说清解决了什么问题、花了什么成本

## 十一、演进方向：多模型角色化协同

在支持多模型派发的框架上，按角色分工：

- 模型 A：需求理解、PRD、整体架构
- 模型 B：独立复核、漏洞挖掘
- 模型 C：落地实现
- 模型 D：代码审查、验收测试

双向制衡的流程是：A 设计，B 挑错，A 修复，B 和 C 独立实现，A 核验实现有没有对齐设计，B 独立质检，问题回流再修。

目标是形成互相校验、互相纠错的闭环。前提是统一目标、分级标准和证据体系，否则多模型之间就是无意义的争论，还可能共享同一个盲区。

## 最后

这套工作流的演进路径很清楚：从强流程、强约束、手把手指令，转向任务状态驱动、操作反馈、权限管控、独立验证和知识沉淀。

好的 Agent 工作流不是把 Agent 管死，而是在可控的自由度里让它自主执行，同时保证四件事：

**关键决策可追溯，高危操作有授权，交付结果有证据，工程经验可沉淀。**

做到这四点，Agent 的自主性越强，结果反而越稳。
