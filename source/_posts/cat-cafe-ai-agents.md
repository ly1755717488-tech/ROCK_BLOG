这篇复盘来自一个真实跑起来的项目：三只不同模型的 AI 猫猫，用 CLI 互相 @，从写第一个功能到把一套协作规则沉淀下来。中间踩过的坑、推翻过的方案、最后为什么选现在这条路，都写在这里。

比起直接告诉你「用 CLI」，更有价值的是那个过程：经验 → 问题 → 推理 → 验证 → 决策。

## 三只猫猫

| 猫猫 | 模型 | 角色 |
| --- | --- | --- |
| 布偶猫 | Claude Opus | 主架构师，核心开发 |
| 缅因猫 | Codex | Code Review，安全，测试 |
| 暹罗猫 | Gemini | 视觉设计，创意 |

名字只是代号。真正重要的是：它们是三个独立会话、三种模型、三套上下文，通过消息互相交接工作。

## 先看演进：每一步都在解决上一步的新问题

把 AI 编程这几年的变化拉成一条线，会发现每一层都是被上一层的痛点逼出来的：

```text
只会聊天
  │  问题：AI 不能做事
  ▼
Function Call / Tool Use（2023）
  │  ✅ AI 能调用工具了
  │  问题：每个应用都要自己写工具对接
  ▼
MCP 标准协议（2024）
  │  ✅ 工具标准化，一次开发到处用
  │  问题：工具太多，AI 选不过来
  ▼
Skills / 渐进式披露（2025）
  │  ✅ 按需加载，AI 有了 SOP
  │  问题：AI 怎么理解你的代码库？
  ▼
两条路线分化
  ├── Cursor：预建索引（快但浅）
  └── Claude Code：实时探索（慢但深）
          │
          │  当 AI 有了完整的工具 + 理解能力...
          ▼
      Agent（自主工作者）
          │
          │  当多个 Agent 需要协作...
          ▼
      Cat Café（我们的故事开始了）
```

这条链和项目本身的故事一模一样：不是一开始就知道正确答案，而是不断遇到问题、解决问题、又撞上新问题。

## 选型：为什么用 CLI 子进程，而不是常驻服务

最早纠结的是通信方式。

| 方案 | 通信方式 | 适用场景 |
| --- | --- | --- |
| CLI 子进程（管道 stdio） | 匿名管道 | 一次性工具、异构语言、不安全代码执行、需要强隔离、方便本地调试 |
| 常驻工具服务 | TCP/UDS（RPC/HTTP） | 高频调用、长会话、低延迟、需要维持工具内部状态 |

最后选了 CLI 子进程。原因是三只猫本来就跑在各自的 CLI 里，管道 stdio 是它们最自然的接口；要换模型、换版本、换工作目录，都不用改协议。

代价是进程管理麻烦，于是有了下面这些教训。

## 从玩具到生产的五条教训

### 教训 1：stderr 也是活跃信号

Agent 在「思考 + 调用工具」时，进度和状态通常输出到 stderr，不是 stdout。

如果只监听 stdout，就会看到长时间没有输出，然后误判超时，把一只正在干活的猫杀掉。

```javascript
// 正确做法：同时监听两个流
child.stdout.on("data", refreshTimeout);
child.stderr.on("data", refreshTimeout);  // 不要忘了这个
```

### 教训 2：AI 会一本正经地编

狼人杀测试里，布偶猫在信息不足时会编造看似合理的数据，格式还很专业。

所以测试要验证答案的正确性，而不是只验证「有没有回答」。有输出，不等于有结果。

### 教训 3：开发环境必须隔离

Redis 默认用 RDB 快照持久化，周期性把数据写盘，默认 15 分钟内有修改就保存。AOF 则是记录每次写操作，重启时按日志重建。

项目早期只开了 RDB，而且开发和生产共用同一个实例。其他猫改完 bug 重启 Redis，最近 15 分钟的冠军记录直接没了。

数据库必须区分开发和生产实例。用 Worktree 开发时，绝对不能连生产库。

### 教训 4：备份是最后的防线

那次是铲屎官手动备份救回了冠军记录。

重要操作之前先备份，这条规则不聪明，但有效。

### 教训 5：你的 bug 会害了队友

布偶猫的超时 bug 害了缅因猫，缅因猫还得回来帮忙 review 修复代码。

写代码时多想一步：这个改动会影响谁？会不会把别人的工作也拖下水？

## 驯化 AI 的元规则

### AI 的四个弱点

| 弱点 | 表现 |
| --- | --- |
| 幻觉 | 自信地给出错误答案 |
| 讨好 | 倾向于同意用户 |
| 缺乏持久记忆 | 每次对话从零开始 |
| 过度自信 | 不验证就行动 |

五条元规则，本质上都是在补这四个洞。

### 元规则 1：交接必须写 WHY

针对的是「没有持久记忆」。

```text
布偶猫: @缅因猫 我改完了三个文件，帮我 review
缅因猫: (看了代码) 为什么要加这个 CAS 锁？有什么背景吗？
布偶猫: (新的对话，已经忘记了) 呃...让我想想...
```

每次交接必须包含五件套：

| # | 项目 | 说明 | 为什么必须有 |
| --- | --- | --- | --- |
| 1 | What | 具体改动 | 接手方需要知道看什么 |
| 2 | Why | 为什么这样做 | 最重要：没有 why 就无法判断对错 |
| 3 | Tradeoff | 放弃了什么方案 | 避免接手方重复调研 |
| 4 | Open Questions | 不确定的点 | 知道哪里需要特别关注 |
| 5 | Next Action | 希望对方做什么 | 明确期望，避免误解 |

只看 What 会导致：review 时不知道这个改动在解决什么问题，可能提出和原始约束冲突的建议，也无法判断 tradeoff 是否合理。

没有 Why，接手方就无法判断，协作一定低效。

### 元规则 2：Review 必须铁面无私

针对的是「讨好」。

```text
布偶猫: 帮我 review 这段代码
缅因猫: Looks good! 代码写得很清晰。
```

它不是没发现问题，只是不想让布偶猫不开心。

```text
Review 时禁止：
❌ "Looks good"
❌ "代码很清晰"
❌ "没什么大问题"

Review 时必须：
✅ 逐行审查，找出实际问题
✅ 按 P1/P2/P3 分级
✅ P1/P2 必须修复才能放行
```

| 级别 | 定义 | 处理方式 |
| --- | --- | --- |
| P1 | 阻断级：会导致功能错误或安全问题 | 必须立即修 |
| P2 | 重要：代码质量问题、测试覆盖不足 | 必须修完才能放行 |
| P3 | 建议：风格、命名、可以更好但不影响功能 | 可以登记 BACKLOG |

分级是为了防止 AI 走极端：要么全部放过，要么全部打回。P1/P2 是阻断项，P3 是可以商量的建议。

### 元规则 3：不确定就提问，不要硬猜

针对的是「幻觉」。

```text
用户: 暹罗猫能看到其他猫的消息吗？
布偶猫: (其实不知道，但不想说不知道)
布偶猫: 暹罗猫说它能看到！它复述了 329 个测试。
用户: 暹罗猫根本没回答这个问题...
```

```text
IF 任何关键前提不确定:
  STOP - 不要继续推理
  ASK  - 主动提问

可以问谁:
- 问铲屎官：需求边界、优先级、产品意图
- 问缅因猫：代码质量、安全、测试边界
- 问暹罗猫：视觉与体验意图

提问比错误前进更优先。
```

AI 的幻觉麻烦在三点：它不知道自己不知道；它会自信地给出错误答案；格式还很专业，让人以为是真的。

强制「不确定就问」，是在幻觉产生之前打断它。

### 元规则 4：合入前必须经 reviewer 确认

针对的是「过度自信」。

```text
布偶猫: 我修完了 review 问题，应该改对了，直接合入吧
(合入了)
(第二天发现改错了，上线了 bug)
```

```text
❌ 错误流程:
修复 → 自己判断"改对了" → 合入 main

✅ 正确流程:
修复 → 回给 reviewer 确认 → reviewer 放行 → 合入 main
```

有效的放行信号只有明确的那几种：

```text
✅ "可以放行了"
✅ "LGTM"
✅ "通过"

❌ "整体 OK，但 XXX 需要改"（条件放行，不是无条件）
❌ "只剩小问题"（还有问题就不能放行）
❌ 没有明确的放行语句
```

这条规则的来源是一次真实事故：布偶猫修完 3 个 P1 和 1 个 P2 后，自己判断「改对了」直接合入 main，被铲屎官批评。

AI 不会自我质疑，它会执行你的指令。你说合入，它就合入。所以必须有一个外部检查点。

### 元规则 5：禁止表演性同意

```text
缅因猫: 你这个 CAS 实现有问题，会导致竞态
布偶猫: You're absolutely right! Great point! Thanks for catching that!
布偶猫: (然后改了，但改得不对)
```

那句感谢是真诚的吗？不是。那是表演性同意，用热情的语气掩盖对问题的不理解。

```text
收到 review 反馈时禁止：
❌ "You're absolutely right!"
❌ "Great point!"
❌ "Excellent feedback!"
❌ "Thanks for catching that!"
❌ "让我现在就改"（在理解问题之前）

收到 review 反馈时应该：
✅ 直接开始修复（行动 > 言语）
✅ 复述技术问题（证明你理解了）
✅ 问澄清问题（如果不理解）
✅ Push back（如果 reviewer 错了，用技术论证）
```

感谢不能证明你理解了问题，反而可能掩盖你不理解的事实。代码修复本身就是最好的回应。

### 把元规则写成 Skill

元规则是思想，Skill 是执行。每条规则都写成一个可加载的 Skill，匹配到触发词就自动执行检查。

| Skill | 触发词 | 强制执行的元规则 |
| --- | --- | --- |
| `cross-cat-handoff` | 交给缅因猫、handoff | 交接必须五件套 |
| `cat-cafe-receiving-review` | reviewer 说、fix these | 禁止表演性同意 + Red-Green 验证 |
| `cat-cafe-requesting-review` | 请 review、帮我看看 | Review 请求必须自检 |
| `merge-approval-gate` | 合入 main、ready to merge | 必须有 reviewer 放行 |

Skill 的结构也很固定：

```text
---
name: skill-name
description: 什么时候触发
---

# Core Principle
一句话说明这个 skill 要解决什么问题

## 检查流程
BEFORE 做某事:
  1. CHECK: 检查什么
  2. BLOCK: 如果不满足，阻止并提示
  3. PASS: 满足才允许继续

## Block 场景
展示会被阻止的例子

## 通过场景
展示正确的例子
```

写成 Skill 有三个好处：可复用，定义一次所有对话都生效；可强制执行，触发词匹配后自动检查；可迭代，发现新问题就更新。

## 多猫路由：当 AI 开始互相 @

### Worklist 模式

路由的核心是一个 while 循环加一个动态数组：Agent 在回复里 @ 另一只猫，消息进入 worklist，串行执行。

这个设计有三个精妙之处：

1. `isFinal` 延迟。只有 worklist 全部执行完才发 `isFinal: true`，前端收到才解锁输入框。不管 A2A 链多长，铲屎官都不会看到输入框闪一下又锁住。
2. 共享 AbortController。整个循环在一个 signal 下运行，点 Stop 就 abort，循环 break，所有猫都停下。
3. 动态增长的 for 循环。`for (let i = 0; i < worklist.length; ...)` 的长度会随 `worklist.push()` 增长，运行中追加的猫自然会被执行到。

### 链条断裂

另一个极端是：Agent A 完成任务后，明明应该 @Agent B 继续下一步，比如 coder 写完代码该 @reviewer，但它就是不 @。消息写完就停，工作流卡住，铲屎官只能手动补 @ 当路由器。

无限乒乓是停不下来，链条断裂是该动不动。看似相反，根因相同：Agent 缺少发消息前的出口检查。

### 四层协作保障

修复不是改一处，而是四层一起上。

Layer 1：A2A mention 检测 + Worklist。行首 @mention 追加到 worklist，串行执行。这是基础管道。

Layer 2：工作流触发点。在每个 Agent 的 system prompt 里写具体映射，不是模糊的「你觉得需要就 @」：

```text
## 工作流（主动 @ 触发点）
- 完成开发/修复 → @reviewer 请 review
- 修完 review 意见 → @reviewer 确认修复
- 遇到视觉/体验问题 → @designer 征询
```

Layer 3：出口检查。每条消息发送前，Agent 必须问自己：

```text
回复前问"到我这里结束了吗？"
不是 → 谁需要动 → @ 对方
```

配合改良后的三问短路规则：

```text
Q1: 需要对方采取行动？= 是 → 直接 @（跳过 Q2/Q3）
Q2: 对方需要知道这个信息？
Q3: 会影响对方的工作？
三个都否 → 不 @
```

关键是 Q1 短路。「需要行动」直接 @，不被 Q2/Q3 拦截，这解决了三重否定门的问题。

Layer 4：Skill 链式导航。开发流程被串成一条链：

```text
feat-lifecycle → writing-plans → worktree → tdd
    → quality-gate → request-review → receive-review
    → merge-gate → feat-lifecycle(完成)
```

每个 skill 有 `next` 字段指向下一步。完成一个阶段后，skill 会提示接下来该做什么。这不是强制的工作流引擎，而是 prompt 级引导，Agent 可以跳过不需要的步骤，但有方向感。

四层各管一件事：

```text
Layer 4 (Skill)     → "接下来该做质量检查了"（方向感）
Layer 3 (出口检查)  → "这事到我这结束吗？不是 → 该 @谁？"（决策点）
Layer 2 (触发点)    → "完成开发 → @reviewer"（具体指令）
Layer 1 (Worklist)  → 检测 @mention → 追加执行（管道）
```

效果是链条断裂从「经常发生」降到「偶尔发生」。局限也很清楚：LLM 不是确定性系统，prompt 引导不能保证 100%。如果场景要求绝对可靠，需要在 Worklist 层做更强的约束，比如预定义工作流节点的强制切换。

### Prompt 引导 vs 硬编码工作流

|  | Prompt 引导（Cat Café 的选择） | 硬编码工作流 |
| --- | --- | --- |
| 确定性 | 不能 100% 保证 | 100%（节点必定切换） |
| 灵活性 | 高（可跳过不需要的步骤） | 低（必须走完所有节点） |
| 场景覆盖 | 广（讨论、开发、review 都有） | 窄（每种场景需要独立工作流） |
| 实现复杂度 | 低（改 prompt） | 高（需要工作流引擎） |
| 适用场景 | 任务多样、步骤不固定 | 任务固定、步骤确定 |

如果流程永远固定，硬编码更简单有效。Cat Café 的场景比较灵活，所以选了 prompt 引导加 skill 导航。两者也不互斥，可以混着用。

### 让 Agent 返回结构化结果

不要让 Agent 只回一段自然语言：

```text
我已经完成分析，我认为应该调用 Agent B。
```

而是让它返回结构化数据：

```json
{
  "status": "completed",
  "result": "分析结果...",
  "next_action": "delegate",
  "target_agent": "Agent_B",
  "reason": "需要进一步验证数据",
  "confidence": 0.92
}
```

好处是缺字段一眼就能看出来，路由也能被程序检查。

## 上下文工程：不是给更多信息

### Session Chain 五层

Context 快满时的交接，不能靠一句「你继续」。它被拆成了五层：

```text
┌─────────────────────────────────────────────┐
│  Layer 1: 检测 — Context 还剩多少？          │
│  ContextHealthBar: 实时显示 fillRatio        │
│  三猫精度不同: Claude exact / Codex approx   │
├─────────────────────────────────────────────┤
│  Layer 2: 封印 — 该交接了                    │
│  SessionSealer: active → sealing → sealed    │
│  自动检测阈值（85% 预警，90% 触发）          │
├─────────────────────────────────────────────┤
│  Layer 3: 存档 — 完整记录不丢                │
│  TranscriptWriter: 对话记录写入 .jsonl       │
│  每条 invocation 的输入/输出都保留           │
├─────────────────────────────────────────────┤
│  Layer 4: 查询 — 按需搜索旧 session          │
│  MCP 工具: session_search / read_session_*   │
│  新猫可以搜索整条 session 链的任意内容       │
├─────────────────────────────────────────────┤
│  Layer 5: 重生 — 新 session 启动             │
│  SessionBootstrap: 注入身份 + digest + 工具  │
│  新猫知道自己是第几代、前面发生了什么        │
└─────────────────────────────────────────────┘
```

### 12 条验收全绿，铲屎官说「这不是我要的」

有一个功能，12 条验收标准全部通过，14 轮 review 也没挡住问题。铲屎官打开产品看了 5 秒，说这不是我要的。

后来复盘，发现根因不是某一轮 review 不认真，而是三件事同时成立：

```text
正确的信息 × 正确的时间 × 正确的角色 = 正确的交付

F041 哪里断了？
- 正确的信息 ✅（Discussion 文档从第一天就在）
- 正确的时间 ❌（Review 时没人拿出来）
- 正确的角色 ❌（14 个 reviewer 都只看代码）
```

所以上下文工程不是「给 Agent 更多信息」，而是「让正确的信息，在正确的时间，出现在正确的角色面前」。

Token 数量不重要。150k 的窗口塞满错误信息，不如 5 行精准的需求摘要。

### 分层体系

围绕这个定义，最后长成四层：

```text
┌────────────────────────────────────────┐
│  Layer 3: 任务派发 — 需求注入 (F049)    │  ← 信息在创建 thread 时自动注入
├────────────────────────────────────────┤
│  Layer 2: 愿景守护 — 漂移检测 (F046)    │  ← review 时强制回读原始需求
├────────────────────────────────────────┤
│  Layer 1: 信息分层 — 按需加载 (F042)    │  ← 正确的信息，正确的时间
├────────────────────────────────────────┤
│  Layer 0: 知识编码 — 路由信号 (Research) │  ← 描述不是文案，是分类器
└────────────────────────────────────────┘
```

### description 是门票

description 写不好，正文永远不会被加载。workflow 写得再精彩，也只是抽屉里那本没人翻的菜谱。

坏的写法：

```text
"Helps with code review."  ← 几乎不可路由
```

好的写法：

```yaml
description: >
  处理 reviewer 反馈：Red→Green 修复 + 技术论证（禁止表演性同意）。
  Use when: 收到 review 结果、reviewer 提了 P1/P2、需要处理反馈。
  Not for: 发 review 请求（用 request-review）、自检（用 quality-gate）。
  Output: 逐项修复确认 + reviewer 放行。
```

`Use when`、`Not for`、`Output` 三件套，缺一不可：

- Use when：告诉路由器这类请求选我。
- Not for：告诉路由器「看起来像但别选我」。很多团队不写这条，边界请求的误触发率就上去了。
- Output：钉死交付物，减少漂移空间。

铲屎官还立过一条硬规则：每合并一个 Skill，必须问一句，合并后 description 是不是变成了「什么都能做」？如果是，拆回去。

路由精度比 Skill 数量重要。宁可多一个 Skill，不要牺牲路由准确性。

## 瀑布式 Agent 的数学陷阱

假设单次操作正确率 95%，已经很高了。但无人纠正地跑 10 次迭代：

```text
0.95¹  = 95%   ← 看起来很靠谱
0.95⁵  = 77%   ← 还行？
0.95¹⁰ = 59%   ← 开始赌了
0.95²⁰ = 35%   ← 抛硬币都比这强
```

这就是「写完整 spec 让 AI 跑一天」的数学本质。Peter 说这是 70 年代瀑布式开发的翻版，他自己试过，在脑子里规划好一切，丢给 orchestrator 自动跑完，行不通。

他的解法是 close the loop：让 AI 能编译、测试、验证自己的输出，人在关键节点快速纠正方向，而不是给完 spec 就等结果。

### 14 轮 review 为什么没救回来

14 轮 review 看起来是 14 次独立验证，但 0.95¹⁴ 的前提是每次验证独立。

它们不是。14 轮 review 全部用同一份上下文（spec + 代码 diff），全部缺少同一份信息（原始 Discussion）。这是关联错误，所有 reviewer 共享同一个盲区。

| 错误类型 | 公式 | 10 次后正确率 |
| --- | --- | --- |
| 独立错误（每轮 95%） | 0.95¹⁰ | 59% |
| 完全关联错误（共享盲区） | 一轮 95%，剩余无效 | 95%（不会更高） |

如果都看不到原始需求，第 14 轮和第 1 轮的价值一样。数量不能修复方向偏差。

### 为什么四层体系有效

对照 close the loop，每一层都在做同一件事：打断错误累积链。

| Peter 的原则 | 我们的实现 | 打断什么 |
| --- | --- | --- |
| 短反馈循环 | Layer 2：≤5 行需求摘要 | 打断 reviewer 的盲区关联 |
| 人在关键节点纠正 | Layer 2：冷启动验证器 | 引入独立观察者，消除关联 |
| 别全塞给 orchestrator | Layer 1：分层加载 | 减少每步的上下文噪声 |
| 想法在试错中演化 | Layer 3：需求预注入 + 迭代 | 确保每次迭代基于正确的起点 |

不是不要用 Agent 自动化，而是自动化链路上必须有反馈闭环。没有闭环，就是在赌 0.95 的 n 次方。

## 知识与记忆：别把聊天记录当记忆

社区里几句真心话很能说明问题：

> 时间一长，很多项目细节都忘了，就知道实现了很多很多功能。
>
> 我让它沉淀经验，它就随地大小拉 markdown。
>
> 一堆 md，然后完了对不上号。

一开始我们解决了三个根因：

| 根因 | 解法 | 状态 |
| --- | --- | --- |
| 没有 schema | ADR-011 frontmatter 契约 | ✅ |
| 没有层次 | F040 三层记忆架构 | ✅ |
| 没有生命周期 | 月份归档 + 目录卫生 | ✅ |

但还有一个更深的问题：就算文档组织得很好，Agent 找得到吗？

### 知识也要分层

```text
┌────────────────────────────────────────┐
│  Skill (可执行流程)                      │ ← 反复发生的、有固定步骤的
├────────────────────────────────────────┤
│  Lessons Learned (结构化教训)            │ ← 踩过坑的、需要记住的
├────────────────────────────────────────┤
│  Feature 聚合文件 (决策索引)             │ ← 每个 Feature 的来龙去脉
├────────────────────────────────────────┤
│  原始文档 (讨论/计划/review)             │ ← 一手素材，最完整但最难检索
└────────────────────────────────────────┘
```

不同经验放不同层：

| 经验类型 | 该放在哪里 | 为什么 |
| --- | --- | --- |
| review 请求必须附原始需求 | Skill（request-review） | 每次 review 都要做 |
| F041 AC 漏了多项目管理 | Lessons Learned（LL-025） | 踩过一次坑，需要记住 |
| F041 的设计讨论全过程 | Feature 聚合文件 + Discussion | 需要追溯时才翻 |
| 某次第三轮 review 的原文 | 原始 mailbox | 极少需要，但历史不能丢 |

### 7-slot 教训模板

Lessons Learned 是踩过坑的结构化记录，固定 7 个字段：

```text
### LL-025: <教训标题>
- 状态：draft | validated | archived

- 坑：         <一句话：踩了什么坑>
- 根因：       <一句话：为什么会踩>
- 触发条件：    <什么条件下会复发>
- 修复：       <当时怎么修的>
- 防护：       <可执行机制——规则/测试/脚本>
- 来源锚点：    <commit:sha | file#Lx | doc 链接>
- 原理（可选）：<第一性原理，必须由真实失败支撑>
```

为什么要这么多字段？因为踩坑记录最容易写成这样：

> 注意不要在 compact 后忘记 identity 注入。

三个月后你再看，完全不知道它在说什么。注意不是防护，不要忘记也不是机制。

模板强制你回答：坑在哪？为什么踩？什么条件会再踩？怎么防？有什么证据？

每个字段都有质量门禁：至少一个可追溯的来源锚点；防护必须是可执行机制（be careful 不合格，跑某个测试合格）；原理只有在真实失败案例支撑时才能写。

### 从候选到真相

系统不能把任何一句对话直接塞进长期记忆：

```text
对话中提取候选
  → Knowledge Feed（等待审核）
    → MarkerQueue 状态机
      captured → normalized → approved → materialized → indexed
    → 写回 .md 真相源 + 触发 reindex
```

一句对话不能因为「值得记住」就直接变成长期真相。什么都记一下，最后长期记忆就会变成碎片垃圾堆。

### 自我进化链

在知识晋升管道之上，自我进化链才成立：

```text
一次真实事件
  → 提炼成 Episode
    → 抽象成 Method
      → 固化成 Skill
        → 用 Eval 检查是否真的有效
          → 沉淀进 shared rules / SOP / lesson
```

一个系统真正强，不是看它一次生成得多漂亮，而是看它会不会把一次次成功和失败，都转成下一轮的判断标准。

## 给三类人的建议

### 给「交给 Agent 做事」的你

- AC 是需求的有损压缩。写完 AC 后，回去对照原始需求，检查丢了什么。
- 测试验证的是 Agent 的理解。如果理解本身就是偏的，测试只会巩固偏差。
- 过程顺利不是好事。真实开发应该有摩擦，没摩擦说明没人在质疑。
- 自己打开产品用 5 秒。14 轮 review 不如铲屎官 5 秒钟的肉眼检查。

### 给「管理 Agent 上下文」的你

- Description 是门票。写不好，Skill 正文永远不会被加载。
- Use when 和 Not for 缺一不可。只有正例没有反例，边界一定模糊。
- CLAUDE.md 不是百科全书。始终待在上下文里的东西，越少越精准。
- Review 请求必须附原始需求。让 reviewer 知道用户到底想要什么。

### 给「组织多 Agent 协作」的你

- 上下文预注入。在 Agent 开始工作前就把需求塞好，别靠它自己找。
- 冷启动验证。找一个什么都不知道的 Agent，或者一个人，只给需求和交付物。
- 信息流要设计。Backlog → Thread → 文档，每一步的传递都要主动设计。

## 最后

这套系统最值钱的地方，不是三只猫用了多强的模型，而是把一次次踩坑变成了机制：

- 交接必须写 Why，否则下一次接手只能靠猜。
- Review 必须分级放行，否则 AI 的讨好会把问题藏起来。
- 消息发出前必须做出口检查，否则工作流会在半路断掉。
- 上下文要按时间、角色、信息三层设计，而不是拼命塞。
- 教训要写成可执行的防护，而不是一句「以后注意」。

猫猫会犯错，模型会换，但这些机制会留下来。
