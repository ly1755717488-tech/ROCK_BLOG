市面上讲 Agent 工作流的框架不少，真正能拿来用的没几个。我用下来的判断标准有四个：

- **机械校验**：能不能不靠 AI 自觉，用程序硬规则给结果打分、给退出码
- **干净上下文派发**：给 Agent 的是不是「当前这件事需要的全套材料」，而不是一大段聊天记录
- **资产分层**：文件、权限、资源有没有分开管，各层只干一件事
- **对抗式复核**：审核的那一方是不是真的独立，敢不敢挑错

OpenSpec、Superpowers、Trellis 三家在这四项上各有强项，没有一家四项全满分。所以最后是拼起来用。

## 同一套东西，分三层看

![表层、中层、底层的三层理解](/img/agent-workflow-tools/01-three-layers.png)

**表层**是看得见的部分：文件夹怎么建、敲什么命令、每个能力叫什么名字。照着抄几天就能复刻。

**中层**藏在提示词里，是四条核心玩法：机械校验、干净上下文派发、资产分层、对抗式复核。这层光看文档看不明白，得扒人家的提示词才知道怎么运转。

**底层**是权衡逻辑：门禁松紧取决于三件事，模型聪不聪明、这件事搞砸的风险多大、愿意花多少 token 钱。这层没有标准答案，只能在项目里反复试错校准，抄不来。

## OpenSpec：管的是人和 AI 的共识

一句话总纲：OpenSpec 是个定需求、改需求、留证据、少扯皮的规矩集，落点不在写代码上。

项目翻车经常不是因为 AI 笨或者程序员不行，而是当初说好要做什么，只留在聊天记录里。聊完就散，两周后没人记得约定；改来改去没有记录，想对比改了哪里、为什么改，根本做不到。

### 核心主张：早点发现方向错，成本最低

和 AI 协作的常见路径是聊着聊着定方案，AI 直接开工。万一需求本身想歪了，几百行代码出来才发现，返工非常麻烦。

OpenSpec 的做法是把大家达成一致的约定单独拎出来，做成和代码一样能进 Git、能校验、历史改不动的东西。重点在管住「共识」这件事，而不是产出文档。

### 两条公理

1. `specs/` 存系统当前真实稳定的规则和行为，也就是真相。不能随手改，要走走正式变更流程才能归档。相当于项目的基线说明书。
2. `changes/` 一次改动开一个文件夹，里面放打算怎么改、改完规则变成什么样、设计思路、待办任务。这些是还在飞、没落地的变更。

好处很直接：评审只看这次改了啥，不用通读全文；多个改动能并行讨论；历史永久保留，以后既能看到改成什么样，也能看到当初为什么这么改。

### 三条分离

**稳定真相和临时改动分开。** 不重写整本说明书，只写增量：新增、修改、删除、重命名。像改合同只附一份变更协议。这也是它适合存量老系统的原因，老系统最怕每次改需求就重写全套文档，写着写着文档就和真实系统脱节了。

**流程规则和执行外壳分开。** 要产出哪些文件、文件之间谁依赖谁、每种文件怎么写，全写在配置文件里。AI 和 CLI 工具只是跑腿的壳子，换了壳子，做菜逻辑不变。菜谱是 schema，锅碗瓢盆是 skill。

**约束规则和最终产出分开。** 提示里明确写着，这些项目规矩只是干活时的参考，别抄进交付文档。每次也只给当前任务刚好需要的信息，避免把一堆提示词混进正式文档。

### 三层判定：谁来判断对不对

这套设计刻意不让 AI 审自己，三层权限切得很清楚：

1. **机器判格式**：工具检查文件结构和格式，错了直接拦，CI 卡住。死板，但有明确对错。
2. **AI 判语义，仅供参考**：AI 核对改动描述和原有规则有没有矛盾、逻辑顺不顺。证据不足就老实标「无法核验」。AI 说没问题不算通过，也没有一票否决权。
3. **人判价值和方向**：开始前看计划，判断这个改动值不值得做；最后看落地代码，判断做出来行不行。

克制点就在这：机器管格式，AI 帮忙找疑点，人拍板。审批权不给 AI。

### 它固定偏好的取舍

| 偏好 | 不喜欢 | 承认的代价 |
| --- | --- | --- |
| 事情要能被客观检查判定 | 把 AI 做得更聪明、自动搞定一切 | AI 保证不了语义正确，对错还得复核 |
| 给推荐路径（建议） | 硬卡死、一步都不能跳的强制门禁 | 人可能偷懒跳步骤，只能靠后续校验兜底 |
| 只有一个正规入口改基线文档，改前先自检 | 随手就能改说明文档 | 正式流程麻烦一点，步骤变重 |
| 纯文本加 Git 管理 | 专属数据库、私有格式 | 文本放久了会过时，需要持续维护 |
| 找证据证伪、保留台账 | 简单重复跑一遍流程测试 | 复核成本高，一般只用在重要改动上 |

总结一句：OpenSpec 不保证做出来的东西一定正确，但它保证当初说好要做什么、每次改了哪里、为什么改，全都有可查、可对比、可追溯的凭据。AI 是帮手不是裁判，文档是人和 AI 之间的账本。

### 它的四条约束

**一、机械校验。** 格式规矩直接写进代码解析器，分两档：硬错误直接失败，CI 不过、返回失败码，比如位置放错、少了测试场景、FROM/TO 不成对；软警告只在严格模式下拦，属于写作质量问题。它还前后锁两道门，存盘前校验一次，存完再读回来校验一次，防止校验看的是 A 文本、写进磁盘变成 B 文本。

**二、干净上下文派发。** 这跟「少发文字」是两回事。它在 schema 里提前定义好每类产出物需要什么、会生成什么，派活的时候程序自动组装刚好这一件事的全套资料：模板、规则、依赖文件路径、依赖的完成状态。另外三条硬约束：哪怕 AI 之前看过，也必须重新从磁盘读，不信对话记忆；背景规则和最终产出要标清楚，禁止把规则原文复制进输出；不需要它处理的 spec 干脆不发任务，只给一句警告。还支持按需读取，先给标题列表盘点，确定改哪条再发全文。

**三、资产分层。** 契约层 `schema.yaml` 是唯一真相源，依赖关系和先后顺序都在这里，程序用拓扑排序算执行顺序，本身还有优先级：项目配置 > 用户配置 > 内置默认，同时防越权读取和软链接穿透。派发层 `skills` 是薄壳，里面几乎没提示词，只有一行行命令调用，所以能对接三十多种工具。内容层就是 `specs` 和 `changes`，归档时把变更合并进 specs，归档目录只追加不改写，跨仓库时上游需求只读。

**四、对抗式复核。** 复核 Agent 只有读权限，不许改代码，目标是挑错证伪。切片做完时并行跑三路：一路对照规格看功能，一路高强度代码评审，一路审提交范围。三路都只提问题，bug 修完才允许串行跑优化。最终整体验收四路拷问：高强度代码评审、全量变更评审、32 个 Agent 分 6 个角度专门证伪找反例，再加一个专门问「我们还漏了什么需求」。

## Superpowers：把纪律压在测试形态上

Superpowers 的假设很直接：AI 代理不靠谱，会撒谎、会失忆、会被长上下文带偏。所以它搭了一套硬流程和隔离机制，逼着 Agent 没法糊弄自己。

### 主流程

头脑风暴挖出真实需求和方案，产出设计文档，人批准；写计划，精确到每步一个动作，人批准并选执行模式；建 worktree 隔离环境，确认测试基线全绿；逐任务实现，每个任务内部走 TDD 红绿循环，写失败测试、看它失败、最小实现、看它通过、提交；子代理模式下每个任务还要过规格和质量双裁决审查；全部完成后由最强模型做全分支终审；最后测试全绿，人从固定菜单里选合并方式。

贯穿全程的两条纪律：证据先于结论，审查是门禁不是建议。

和 OpenSpec 对比很有意思。Superpowers 的把关点在测试形态，TDD 红绿、worktree 基线、子代理双裁决、最强模型终审；OpenSpec 的把关点在规格形态，没有强制 worktree、没有强制 TDD、没有多模型审查，纪律放在规划阶段不许写代码、delta 必须能合并、勾选必须有代码证据这三处。所以 OpenSpec 更轻、更贴存量项目，执行质量的下限更依赖自己补测试门禁，这也是它文档里承认的代价。

### 四条约束

**一、机械校验。** 不许口头宣称成功，想说过关就得跑命令、拿退出码和完整输出、看 diff、看测试红绿。它还专门划了真假证据：格式化工具不报错不等于能编译；AI 说改好了不等于真改了，要看 git 改动；测试得跑完一轮先失败再修好，才算验证闭环。它自己也用脚本管自己，限制核心规则文件大小、检查目录结构、pre-commit 做类型检查。

**二、干净上下文派发。** 派活前单独生成一份精简任务文档，小弟只看这份，看不到之前的聊天。产出写成报告文件传回，只回极简状态和版本号，大块内容不塞回对话。禁止小弟再派更小的小弟，防止套娃。进度写在独立的 ledger 里，不靠对话记忆，因为真发生过控制器失忆、把做完的活又派一遍。

**三、资产分层。** 主规则文件 `SKILL.md` 硬性限制在 2 万字符以内，因为 Claude Code 读到这里会截断。所以拆开：SKILL.md 常驻且短小；各类 prompt 模板单独成文件；references 放不常用的复杂分支流程，走到对应步骤才读；测试脚本单独隔离，避免 AI 把测试代码当成要执行的指令。

**四、对抗式复核。** 实现者和审查代理是两个独立角色。审查者拿到的也是干净需求、diff 和规范，看不到主控制器的聊天，不受主代理影响。审查要分两件事：符不符合需求文档、代码质量好不好，自查不算正式审查。收到意见不能客套认下，要先核验，审查错了拿技术理由反驳，讲道理优先。最关键的一条，派活的人不能提前给审查者打招呼放水，写「这块不用重点查」本身就是违规。问题也不许偷偷删，要么修好，要么到上限后由主代理裁决并记进台账。

## Trellis：把工程制度写进仓库

Trellis 不追求让 AI 变聪明。它把所有规矩、资料、进度变成仓库里的文件，靠脚本在对的时机喂给 AI，专门治失忆、乱拿资料、偷偷跳步骤、规范没人落地这几个毛病。

### 三个病根

**上下文衰减。** 聊天窗口有长度限制，聊久了被压缩，新会话直接清零。之前说好的规矩、踩过的坑，每次都要重讲。解法是把经验存 `journal`，团队规范放 `spec`，文件不会自动消失。

**规范不可靠。** 所有规则堆进一个超大的 `CLAUDE.md`，越写越长，AI 根本看不完，也抓不到重点。解法是拆成小块，这次任务需要哪几条就给哪几条。

**过程不可追溯。** 一大段提示词扔过去，需求改来改去，中间怎么想的、依据是什么，事后查不到。解法是需求、设计、执行清单全部单独成文件，跟着任务状态走，全程留痕。

两条底层信条：先规划再写代码；规范靠系统主动递到 AI 面前，不靠它自己记住。

### 五个设计思路

**文件大于 AI 临时记忆。** 调研结论、踩坑教训、决策理由，全部写成文件进仓库。聊天记录是草稿纸，说丢就丢；spec、journal 是归档文档，下次打开就能读。日志还会自动分页轮转，防止单份文件太大。

**状态机大于一大段提示词。** 任务有明确状态，规划中、执行中、复核中、完成，状态存在文件里。脚本读这个状态，每轮对话前自动注入当前阶段必须遵守的几条规则。而且强制校验：规定要跑的步骤必须留记录，没记录就判定没执行，不许往下走。这些标签不是给人看的说明，是脚本能读、能校验的数据。

**白名单大于一股脑全丢上下文。** 每次干活前，主会话整理一份 `implement.jsonl`，只放本次要用的规范和调研材料，不放马上要改的代码，因为代码是产出，不是参考依据。还有大小上限，超了就降级成索引，不会偷偷删内容。

**三道闸门，把人做决策和机器执行拆开。** `task.py create` 只建任务文件夹，不等于同意开工；`task.py start` 才真正启动，没选好规范参考文件就直接拒绝，除非手动强制放行；规划方案出来后必须人手动确认批准，AI 才能动手写。

**诚实，可以回滚对照。** 它自带消融实验，先备份项目，临时关掉整套约束，开一个不受约束的会话，对比两种模式的产出差别，判断这套制度到底有没有价值，用完一键恢复。文档也不藏短板，废弃功能和坑都写清楚。

### 两条底层原则

**优先查证据，不随便提问。** 调研的 AI 不能随口说「一般来说是这样」，每个技术结论都要附代码原文和行号，找不到证据就删掉这句话，宁可空着也不编。能查仓库就别随便问人。

**不完全相信 AI 的审核结果。** 预设 AI 评审大约 35% 的告警是误报，严重问题必须人工去源码核对。审核 AI 只能修格式、导入这类机械问题，架构设计问题只能提意见，不能私自改方案。

### 它承认的短板

小修改走全套流程很麻烦，所以留了 `no-trellis` 逃生开关。spec 没人维护就会慢慢过时。有些接入方式只能靠 AI 自觉，管控力度弱一点。

适合长期维护、多人协作、代码重要的项目；不适合一次性脚本和快速原型。

### 四条约束

**资产分层。** `spec` 是规范文档，公司手册，人和 AI 都能写；`tasks` 一个任务一个文件夹，主会话创建；`journal` 是个人干活记录，只给自己看，不跟别人冲突；`workflow` 和 `agents` 是岗位说明书，规定哪个 AI 按什么顺序干。每次任务只挑两条三条真正需要的规范给 AI。这里还有个容易混的点：`implement.md` 是人看的执行清单，`implement.jsonl` 是机器读的白名单。

**干净上下文派发。** 主会话先写好白名单，派发瞬间脚本把清单里的文件原文塞给小弟，而不是给个路径让它自己读。不继承父对话、不接着上次会话、不分段续聊，纯冷启动。资料包有大小上限，超了只给文件名和简介。提交和合并权限只有主会话有，干活的不能提交。

**机械校验。** 启动闸门：一份规范参考都没配，直接不让跑，防止裸奔。提交闸门：提交前自动格式化、跑 lint 和测试。CI 闸门：推上去校验语法、类型、编译、打包产物。连上下文注入这套逻辑本身都写了大量单测，还用哈希记录模板文件，区分人工改过的和自动生成的，避免覆盖用户改动。

**对抗式复核。** 单独拉一个 `trellis-check`，看不到开发 AI 的汇报和自我解释，只看代码变更、需求、规范。人设保守多疑，默认找问题。输出必须写清拒绝了哪些备选方案、影响范围多大，不能只给一句没问题。格式和导入错误它可以顺手修，架构判断只提意见，决策权交回主会话。收尾还有一条反向约束：最后关头发现严重问题，优先改 spec，而不是改代码凑合过。

闭环四步：资料分库存放，知道该拿哪些依据；派活不带历史垃圾，依据干净；脚本硬闸门卡死客观指标；独立审核 AI 对抗质疑，管机器看不懂的设计问题。

## 三家怎么分工

按阶段拆开，每家负责自己最强的那一段：

| 当前阶段 | 调用哪个体系 | 用什么 |
| --- | --- | --- |
| 需求探索 | Superpowers | `brainstorming` |
| 技术方案设计 | Superpowers | `brainstorming` |
| 编写开发计划 | Superpowers | `writing-plans` |
| 准备任务上下文 | Trellis | 原有上下文管理 Skill 或脚本 |
| 执行开发 | Superpowers | `subagent-driven-development` 或 `executing-plans` |
| 编写测试 | Superpowers | `test-driven-development` |
| 代码审查 | Superpowers | `requesting-code-review` |
| 最终验证 | Superpowers | `verification-before-completion` |
| 需求规格归档 | OpenSpec | `sync`、`archive` |
| 重要决策沉淀 | DeepSeek Harness | `write-notes-like-deepseek` |

![实际调用关系：哪个阶段用哪套体系](/img/agent-workflow-tools/02-call-chain.png)

具体入口名以实际安装版本为准，有些是 Skill，有些是 Slash Command，有些是 CLI 脚本。

## 知识沉淀：write-note-like-deepseek-harness

这套工作流里最容易被忽略的一环是沉淀。write-notes-like-deepseek 把 DeepSeek 团队维护代码库的方法做成了可安装的 Skill，五个点值得说。

**沉淀的是为什么。** 代码只能表达系统现在怎么跑，表达不了当初为什么这样定、放弃了什么。它强制把决策背景、被放弃方案的最强理由、收益和代价写成笔记。后人看到的不再是一段别扭的代码，而是背后的约束和权衡。

**规矩写在绕不开的地方。** 笔记放在 `.agents/notes/`，AI 工作时必然读到；代码和笔记同一次提交，笔记不会掉队；树结构、类别、格式、备选方案都有脚本校验，违反就非零退出。用它的原话说，你不需要相信 AI 的自觉，只需要相信非零退出码。归档笔记记进 manifest 的 SHA-256，只增不改，篡改当场报警。

**目录即状态。** `proposed / implemented / rejected / archived` 四个目录直接表达生命周期，配六种固定分类：feature、bug-fix、simplification、architecture、process、testing。多分支并行也不会出现全局索引每改必冲突。

**有准入标准，不搞过度留痕。** 只有非平凡改动才必须留笔记，比如行为变化、架构调整、跨文件契约、流程、测试策略、落盘格式。判断问句很实用：光看代码和单测，后来的人能推导出为什么这样定吗？推导不出就是非平凡。

**知识可检索、可视化。** 避坑智库汇总所有被否决的方案，每条带最强理由，防止重走老路；决策看板一条命令生成单文件 HTML，能看到被引用最多的承重墙决策、血缘链路和演进时间线。它内置了 DeepSeek Harness 的 1267 篇真实笔记，可以脱机浏览，说明这套结构撑得起长期沉淀。

一句话：把知识沉淀从靠自觉写文档，变成靠门禁强制留痕，而且沉淀的正好是代码表达不了、AI 又最需要的那部分，也就是决策的理由和放弃的路。

## 我自己怎么取舍

![我自己那套工作流的调整思路](/img/agent-workflow-tools/03-my-tradeoffs.png)

大方向参考 Trellis 的调度和任务管理、Superpowers 的方法论、write-note-like-deepseek-harness 的记录方式、OpenSpec 的结构。差异集中在这几处：

**硬门禁少而准。** 参考 OpenSpec 的思路，`workflow plan --validate` 这类结构校验必须有，确保格式和机械判断的条件不缺。校核、提交这类动作，有条件硬检验也有危险硬检验。

**软门禁是重点。** Agent 能力比前两年强了，遵从性也好很多。既然把操作都包进了 CLI，那 CLI 的输出本身就可以当软提示用，类似终端里打错命令时提示「你是不是想用这个参数」，比把 Skill 写长有效。

**小而短的 Skill 加一套自己的 CLI。** 归档、用户批准、记录、检验、证据归纳、临时文件清理释放，全走 CLI。commit 和 push 这种高危动作，Agent 调 CLI 时带 `--approve` 之类的设计，所有记录、规划、需要提交的文案和范围落盘之后，没有用户同意就不放行。同意分两种：用户自己在命令行里跑同意指令，或者用户给 Agent 授权。为了防止 Agent 幻觉，软提示之后还要再硬校验一次。如果用户在这个 Task 里已经自主提交过，就写进 task 设置里，后面不再反复问。

**知识沉淀做成机械门禁。** 防止 Agent 特别是子 Agent 忘记录盘，确保任何任务至少有一条，或者明确写明这次没有。

**子代理按成本派。** DSH 的子代理分两种，持久化队员上限 8 个，一次性子代理随时起。最多 8 个并发：干净子代理负责独立复核、检验、收敛检查、调研；队员负责持久任务、可能返修、改动风险大、范围大的活。派任何子代理都有任务量要求，避免一个小任务也开一个子代理白烧 token。

**任务分两类加谱系。** 参考 OpenSpec，任务分活动和归档，活动里有 plan、build、verify 的细分，归档只有 done 和放弃两种。实际干活经常出现做一半发现效果不达预期、或者冒出新的想法，需要交接和新建任务。所以把交接文档和交接要求也做成工作流一部分，再配一个二维任务谱系，记录我们没干完的任务和新建任务之间的派生关系，归档时按关系自动处理。

还没做完的是多模型调度。现在 DSH 已经能派 Codex 智能体了，接着要考虑让不同模型一起干活，互相找茬然后修复。

## 收尾

三套框架放在一起看，结论其实很朴素：没有一套是万能的，差异全在把纪律压在哪一层。

OpenSpec 压规格，Superpowers 压测试，Trellis 压制度和留痕。四把尺子量下来，每家都有一项满分、一项不及格，所以真正落地时大概率是拼装。拼装的前提是先把尺子定下来，知道自己缺哪一项。
